## 核心结论：安装方式变化对 Picot 内嵌 Pi 无影响

上游「installation 方式更新」的实际内容（commit `581e7ba78`，1.0.1 周期）：

- 移除 `npm-shrinkwrap.json`（-1953 行）——npm 安装不再 pin 传递依赖
- 主推 managed installer：`curl -fsSL https://pi.dev/install.sh | sh`，本体落
  `~/.pi/agent/bin/pi`，用 `pi update` 自更新，依赖由 installer lockfile pin
- 1.0.4 release 新增产物：`pi-coding-agent-install-package.json` / `…-lock.json`
  （installer 的 pin 物料）、`pi-1.0.4-source.tar.gz`、`SHA256SUMS`

Picot 三层逐一实测，全部兼容：

| 层 | 上游变化 | Picot 消费点 | 结论 |
| --- | --- | --- | --- |
| Release 产物 | 四平台 tar.gz 保留，命名不变；新增 installer 物料 | `scripts/fetch-pi-binary.js` 按 `pi-<platform>.tar.gz` 下载 + sha256 | **无影响** |
| Tar 内布局 | `pi/` 包装目录；bun 编译自包含二进制；无 node_modules | flatten 后落 `src-tauri/resources/pi/`；实测 1.0.4 与本地 1.0.2 顶层逐项一致，均无 node_modules | **无影响**（bun 自包含早已是现状） |
| 运行方式 | RPC over stdio 面无变化 | `pi_launch.rs:127` 的 node_modules 是用户侧扩展 bin 的 PATH 注入，与内嵌资源无关；L231 仅做 Windows 路径前缀剥离 | **无影响** |

实测：1.0.4 darwin-arm64 tar 解包直跑 `pi --version` → `1.0.4`，Mach-O arm64。

唯一残留：`scripts/fetch-pi-binary.js:20` 注释仍称产物含 `node_modules/`——**过时注释**（1.0.2 起即无），建议顺手修正，不阻塞。

## 用户侧 ~/.pi/agent 数据面（Picot 依赖它的部分）

Picot 产品按 ARCHITECTURE 原则自包含（不要求、不探测用户安装的 pi），免疫于安装方式变化。
但宿主侧有两点漂移值得记录：

1. `pi_launch.rs` 的 `pi_extension_npm_bin_dir`（`~/.pi/agent/npm/…/.bin` PATH 注入）
   在新安装方式下语义仍成立——npm 区现在只装扩展/MCP server，本体不在其中。
2. **宿主 pi 会话的子代理扩展故障根因即在此**：pi-subagents（npm 区扩展）peer 依赖
   `@earendil-works/pi-coding-agent`，旧安装方式下随 pi 本体装在 npm 区；换成 managed
   installer 后 npm 区只剩 `pi-tui`，peer 落空 → spawn 全挂。上游 #10439（pi 被更新/移除
   后 restart hint）说明上游意识到了此类破坏模式。修复方向：pi-subagents 侧改为对
   `~/.pi/agent/bin/pi` 安装布局的解析，或随 Dr. Lin 的 pi 安装方式统一处理。
