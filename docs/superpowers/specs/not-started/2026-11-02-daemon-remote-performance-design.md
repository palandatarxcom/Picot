# Daemon 远程连接性能与稳定性：候选优化点

**状态：** Draft，待测量和评审

**范围：** Relay 远程连接；连接建立、断线恢复、会话切换、流式更新、2–5 个客户端并发

**源码基准：** `a789f5d`；以下判断来自静态阅读，尚无远程性能基线。

## 1. 目标与边界

Dr. Lin 观察到远程连接建立较慢、使用中会断线。目标是缩短连接与恢复时间、减少非预期断线，同时改善会话切换和流式更新，并验证 2–5 个客户端并发时的稳定性。先在隔离环境测量，再根据结果选择改动；源码候选点不代表已确认根因，也不要求全部实施。

不改变端到端加密、设备撤销、权限校验、消息顺序或现有协议的安全边界。需要改变协议、消息完整性或溢出行为时，先另行评审。局域网直连不在本次范围。

## 2. 候选点

### 2.1 出站 JSON 重复序列化

**现状。** `src-tauri/crates/picot-host/src/transport_limits.rs:66-71` 的 `serialized_size()` 通过 `value.to_string()` 计算大小；`host_server.rs:1622-1639` 的 `outbound_message()` 校验后再次执行 `value.to_string()` 生成消息。Relay 路径随后还要封装、加密和 Base64 编码。

**假设。** 对大快照和高频事件，重复序列化可能增加 CPU、分配和等待时间；尚不知道占比。

**候选方向。** 在一次出站处理内复用序列化结果，同时对实际发送的 UTF-8 字节执行原有大小限制。不能跳过限制，超限错误的类型和 requestId 关联也要保持不变。

**验证。** 比较小型流式事件与不同大小快照的序列化次数、耗时和分配；检查限制边界、非 ASCII 内容和超限响应。

### 2.2 会话快照串行获取

**现状。** `host_server.rs:3341-3417` 处理 `runtime_snapshot_request` 时，先等待 Pi 的 `get_state`，再请求 `get_messages`，最后把消息列表放入快照。`get_state` 的结果可能用于绑定临时 session ID；在获取消息前还会处理 session file 与 bucket。

**假设。** 两次串行 RPC 及完整消息列表可能拖慢会话切换，尤其是长会话。尚未测得各阶段耗时或消息体积。

**候选方向。** 先量化各阶段；仅在证明目标身份和顺序安全时考虑减少等待或传输量。不预设可以并行调用，也不预设增量快照协议。

**验证。** 分别测量已有运行时和新启动运行时、短会话和长会话；检查临时 ID 绑定、正确会话的消息、错误处理及快照与事件衔接。

### 2.3 设备视图重复读取

**现状。** `host_server.rs:2911-2914` 的 `remote_device_binding()` 在设备视图存在时先调用 `device_view_for()`，再由 `device_view_scope()` 调用同一读取。`remote_auth.rs:92-101,194-202` 经认证锁和共享 metadata 锁读取，`metadata_store.rs:956-975` 查询 SQLite。这发生在调用该绑定检查的请求路径上，不代表每条流式事件都读库。

**假设。** 重复查询及共享锁可能增加远程请求延迟，多个客户端操作时可能发生争用；程度待测。

**候选方向。** 同一次绑定判定复用一次读取的视图；保留后续判定读取最新视图的语义，不跨帧缓存。核对所有调用者及导航、撤销和并发变更的行为。

**验证。** 统计一次绑定判定的视图读取次数及并发等待；回归测试确认视图更新后下一次判定可见，设备撤销与授权结果不变。

### 2.4 慢客户端与中间无界队列

**现状。** `host_server.rs:2044` 的会话出站队列以及 `host_server.rs:2541-2542` 的 Relay 桥接入站、出站队列无界；`relay/transport.rs:119-134,719-724` 的最终出站队列有界，满时关闭当事连接。Relay socket 的发送端不会因桥接出站队列积压而等待（`host_server.rs:2476-2497`）。

**假设。** 慢客户端或加密速度跟不上事件产生速度时，中间队列可能积压，增加内存与消息延迟。最终有界队列可能关闭慢连接；积压规模及发生条件尚未测量。

**候选方向。** 根据测量确定是否需要限制 Relay 中间队列或传播背压。必须明确容量单位、满队列处理、消息顺序和连接关闭语义，并验证不会拖慢其他客户端；共享会话管线的 loopback 行为不能无意改变。

**验证。** 模拟慢消费者和突发流式事件，记录队列或内存峰值、消息延迟、关闭与丢失情况；同时检查其他客户端仍可交互。验证撤销和断连时的清理。

## 3. 连接慢与断线：稳定性专项

连接慢与断线是用户观察到的现象；发生频率、网络条件和根因尚未确认。以下是源码中需要核查的路径，不是已证实的故障原因。

| 候选因素 | 源码事实 | 待核实的问题 |
| --- | --- | --- |
| 建连和重连排队 | `relay/transport.rs:496-537,605-623,700-712` 在同步时为客户端启动独立 data socket；E2EE 握手限制为 4 个，排队计入 10 秒预算（`transport_limits.rs:39`）。 | 5 个客户端同时连接时，第 5 个等待多久？排队是否造成超时？ |
| 客户端握手等待 | `relay/client_role.rs:50-65` 定义 250ms 预等待、最多 3 次 hello 发送及 15 秒握手预算。 | 建连慢主要发生在拨号、等待 data socket、握手还是应用层 hello？ |
| 心跳与断线判断 | `relay/transport.rs:63-80` 的 control ping 间隔为 10 秒，30 秒无入站帧视为 stale；客户端也有空闲超时。 | 断线是否发生在空闲、网络抖动或后台运行期间？触发的是哪一侧的关闭？ |
| 慢消费者 | §2.4 的最终出站队列满时关闭该 data 连接，中间队列无界。 | 断线是否由队列满触发？当事客户端和其他客户端各看到什么？ |
| 事件接收落后 | `host_server.rs:2399-2400,2425-2433` 对 host event 的 `Lagged` 直接跳过；runtime event 的 `Lagged` 发送 `event_sequence_gap`。 | 是否发生事件缺口或界面状态陈旧？对应恢复路径是否有效？ |
| 共享锁竞争 | §2.3 的认证与 metadata 锁由多个请求共享。 | 并发操作是否造成明显等待或影响连接恢复？ |

### 3.1 测量与故障分类

- 分别记录客户端发起连接到应用层 `hello_ack` 的总时长，以及可观测的 control/data socket、E2EE 握手和应用层 hello 阶段耗时。客户端和 daemon 可能已有存活的 control 连接，应记录复用或新建，不能把两者简单相加。
- 记录意外断线次数和发生阶段、重连成功率与恢复耗时；区分网络中断、control stale、data socket 关闭、握手超时、队列溢出、主动关闭及原因未知。不能区分时如实标记未知。
- 关联事件使用不含凭据的临时标识；不记录 token、密钥、消息明文或其他敏感内容。先核实现有日志，再决定是否需要最小诊断手段。
- 在隔离环境覆盖单客户端与 5 客户端，同时重连、慢消费者、延迟和抖动、短时断网；记录事件缺口、资源释放和未受影响客户端的表现。公网手测另行确认环境。

### 3.2 稳定性验收

- 记录相同网络条件下的连接耗时、意外断线率、重连成功率和恢复时间，比较优化前后；具体性能阈值在基线测量后确定。
- 5 客户端同时重连测试应覆盖许可排队；重复试验并记录失败原因，确认 socket、session 和任务没有持续泄漏。
- 一个慢客户端不得拖慢其他客户端；内存增长和满队列后的关闭语义须可验证。若要改变现有关闭策略，先评审。
- 对事件缺口验证现有恢复机制；不得以隐藏错误或静默丢事件冒充稳定。设备撤销、权限新鲜度和消息顺序保持原有契约。

## 3. 测量与决策

1. 使用隔离数据目录和受控 Relay 夹具。先排查 Rust 测试对真实 `HOME` 的继承及孤儿进程清扫风险，确认测试隔离后再运行；不得以真实用户状态作为测试数据。
2. 用现有 Relay 端到端夹具及真实协议帧，分别测 1 个和 5 个客户端；包含会话切换、流式事件与慢消费者。记录短、长会话、消息体积、网络条件、样本量及预热方式。
3. 记录会话切换和请求往返 p50/p95、流式事件延迟、序列化与设备视图读取次数，以及慢消费者下的内存或队列变化、断连和丢帧情况。性能比较使用相同环境和负载；不在此预设尚无基线的改善百分比。
4. 按测量结果选改动，逐项比较改动前后。若某项无可重复的实际收益，保留证据，不为完成清单而实施。
5. 隔离测试通过后，使用经确认的专用环境做真实跨网络手测，核对会话切换和流式体感。本机模拟不能替代公网验收。

## 5. 验收与限制

- 改动前后数据可复现，覆盖 1 和 5 客户端；记录测试条件和异常结果。
- 保留协议大小限制、权限新鲜度、设备撤销及错误反馈。队列方案不得静默丢失消息或让慢客户端拖垮其他客户端；若方案需改变现有溢出契约，先取得批准。
- 对所选改动添加确定性回归测试，执行相关 Rust 检查和项目测试；真实性能样本不作为易抖动的固定 CI 时限。
- 每项改动保持可独立撤回；撤回不能降低现有安全校验。
- 真实跨网络设备和 Relay 环境尚未指定，手测安排待确认。
